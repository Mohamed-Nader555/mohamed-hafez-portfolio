## The problem

Eklan generates five types of practice drill for each learner every week. They all came from one shared prompt, so each drill type picked its own vocabulary and its own situation. A learner could get five drills that had nothing to do with each other or with what they had studied, and the multiple-choice drills almost always put the right answer first.

## Who it was for

Learners, who should practise one lesson from several angles, and tutors, who want the week's drills to match the week's class.

## My role

I designed and built the prompt composer, the cached lesson-focus service, the scenario templates for a 25-topic by 14-unit matrix, and the feature-flagged rollout.

## What I built

<FeatureGrid items={frontmatter.features} />

The learner block carries more than a level. It includes the weaknesses recorded for that learner, from grading and from tutors' notes, so the drills lean towards what that person actually gets wrong. The scenario block places the drill in a situation from the learner's current unit, and the lesson-focus block names the phrases and sounds the whole week should repeat. The drill-type block is the only part that differs between, say, a vocabulary drill and a fill-in-the-blank drill.

The budget matters because a learner with a long history can produce a very large context. Instead of letting the prompt grow without limit, the composer has a fixed order for what is dropped first when the 9,500-character budget is reached, and unit tests cover each block and each drop.

## How it works

For each drill type, a pure composer assembles the prompt from five blocks under a character budget. A cached lesson-focus call makes every drill type share the same phrases and pronunciation targets, and the composed prompt then goes to generation.

The lesson-focus call is cached per learner, so it runs once and every drill type reads the same result. A lock in the database, with a way to reclaim a lock left behind by a crashed run, makes sure two requests never pick two different focuses for the same learner.

The trade-off is size: composed prompts use about 47% more tokens than the old shared prompt, which I reported along with the gains.

Because the flags kept the old prompts byte for byte when switched off, the change could go to staging dark, be compared there, and be switched on without a second deploy.

## What I learned

> Treat a prompt like code: compose it, budget it, test it, and ship it behind a flag.

Once the prompt was a function of named blocks, the questions changed from "is the wording right" to "which block is missing for this learner", which is a much easier question to test.

## What I'd do next

Measure whether learners retain the shared lesson better across a week, not only whether the drills are longer and less biased.
