    detail: The first stage writes down exactly what the learner said, fillers and false starts included, because fluency and pronunciation feedback is useless on a cleaned-up transcript.

decisions:
  - choice: grade each turn in the background while the call is still running
    over: grading the whole session after the learner hangs up
    because: most of the work can be done before the call ends, so the learner waits for the last turn instead of for the whole session
  - choice: fluency measured in code
    over: asking the model for a fluency score
    because: pace and filler counts are arithmetic; computing them makes the score repeatable and leaves the model only the judgements that need it
  - choice: a narrow fallback plus a stored error reason
    over: guessing at a failure I couldn't reproduce
    because: a rare error deserved a safe path for the learner today and enough evidence to fix it properly the next time it happened
challenges:
  - problem: The transcription model accepts only about 10 requests a minute, and a busy session sends many more.
    solution: Transcription calls run 8 at a time, and a rate-limit error falls back to the grading model instead of failing the turn.
  - problem: One stage occasionally failed with an invalid-argument error that I could not reproduce after many tries.
    solution: I shipped a narrow fallback that retries that clip once on a second model, and stored a short error reason for every part, so the next failure would be visible instead of guessed.
  - problem: An LLM grader is only useful if it gives the same session roughly the same score twice.
    solution: I graded 8 real sessions twice and compared them. The median difference was 1.5 points out of 100 and the largest was 6, which made the scores fit for showing learners.

## The problem

After a voice roleplay, a learner wants to know how they did. The old flow graded the whole session only after the call ended, so learners stared at a loading screen for over a minute, and one failed step could leave the whole report empty. The feedback also had to be trustworthy: a grade that changes every time you ask is worse than no grade.

## Who it was for

Nurses and clinicians practising spoken English, who need specific, repeatable feedback on pronunciation, language, communication and fluency, and the tutors who review that feedback with them.

## My role

I designed the grading pipeline and built it end to end: the five stages, grading during the call, retries, locks and model fallback, the stored status for every part, the calibration check and the staged results page.

The fluency score blends the AI coach's voice notes and the roleplay results 60/40, so it reflects how a learner speaks in both settings.

## How it works

Each learner turn is transcribed word for word, then scored for pronunciation and, in parallel, for language and communication. Fluency is computed in code, and an LLM writes coaching tips from all of the scores. While the call is running, Next.js grades each finished turn in the background, and the results page fills in part by part.

## Results

Grading during the call cut the wait from the end of the call to the full report by 26–41% on two real sessions, and the first result now appears in 0.5 s instead of 20–36 s. These timings were measured in testing against the live models, on a local setup, not from production traffic.

## What I learned

> A pipeline is only as useful as its worst failure. Make each part report on itself.

Splitting grading into parts that each record their own status changed what failure looks like. A rate limit or an odd clip now costs the learner one part of the report for a while, with a reason attached, instead of the whole report. The calibration check mattered just as much: it turned "the model seems consistent" into a number I could stand behind.

## What I'd do next

Repeat the calibration on a larger set of sessions and track it over time, so a prompt or model change that makes grading less consistent is caught before release.
