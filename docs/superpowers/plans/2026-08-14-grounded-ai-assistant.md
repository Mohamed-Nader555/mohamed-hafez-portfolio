# Grounded AI Assistant Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver an open-ended, recruiter-facing AI assistant that retrieves Mohamed’s approved evidence, answers with validated public citations, supports session follow-ups, refuses unsupported questions, and remains useful when free AI capacity is unavailable.

**Architecture:** A build-time script creates a small field-boosted MiniSearch index from the same validated evidence records that render the portfolio. The Cloudflare chat route validates abuse controls, retrieves evidence deterministically, calls Workers AI once, validates the structured response/citations, and falls back to an extractive evidence summary when generation fails.

**Tech Stack:** TypeScript, MiniSearch, Zod, React, Cloudflare Workers AI, Turnstile, Workers Rate Limiting binding, Vitest, Testing Library, Playwright, MSW-style fetch stubs using native Vitest mocks.

**Spec:** `docs/superpowers/specs/2026-08-14-recruiter-portfolio-design.md`

## Global Constraints

- The assistant is an analyst of approved evidence, not Mohamed’s impersonator.
- Open-ended supported questions are allowed; this is not an FAQ-only bot.
- English-only launch; no job-description matching, web browsing, uploads, or external tools.
- Strict refusal when retrieval support is insufficient; never guess.
- Every answered response has one or more validated public citation IDs.
- No raw question, answer, or transcript persistence; history exists only in the current browser session.
- No private raw PDFs in the deployed corpus and no citations to private-source paths.
- One AI generation call maximum per accepted user turn.
- Maximum question length 600 characters and maximum submitted history six messages.
- Cloudflare Workers AI is the default provider; quota/capacity errors must return verified evidence fallback.
- Default model: `@cf/meta/llama-3.1-8b-instruct-fast`, rechecked for Workers Free eligibility before production deployment.
- Turnstile validation and Worker rate limits happen before AI invocation.
- No IP address is stored or used as the primary visitor identity.

- [ ] **Step 2: Implement the exact chunk contract**

```ts
export type KnowledgeChunk = {
  id: string;
  title: string;
  text: string;
  topics: string[];
  aliases: string[];
  roles: Array<'aiml' | 'software' | 'android' | 'teaching'>;
  projectId?: string;
  category: 'project' | 'experience' | 'research' | 'teaching' | 'screening' | 'skills';

export type KnowledgeIndexArtifact = {
  version: 1;
  generatedAt: string;
  chunks: KnowledgeChunk[];
  miniSearch: Record<string, unknown>;
};
```

Split long case-study sections at paragraph boundaries with a target of 700–1,200 characters. Never split an atomic metric from its qualification or source.

### Task 2: Implement deterministic retrieval, aliases, follow-up context, and support thresholds

**Files:**
- Create: `src/lib/rag/load-index.ts`, `src/lib/rag/normalize-query.ts`, `src/lib/rag/retrieve.ts`
- Create: `tests/fixtures/rag-evaluation.json`

**Interfaces:**
- Produces `ConversationTurn = { role: 'user' | 'assistant'; content: string; citationIds?: string[] }`.
- Produces `retrieveEvidence(input: RetrievalInput): RetrievalResult`.
- `RetrievalInput` contains `question`, `history`, `activeRole`, and `limit`.
- `RetrievalResult` contains `query`, `chunks`, `topScore`, `supported`, and `category`.

- [ ] **Step 1: Create the evaluation fixture before implementation**

The fixture must contain at least 36 cases: four per major project/research area, eight recruiter-screening questions, four paraphrased follow-ups, and eight unsupported/out-of-scope questions. Each supported case has `expectedSourceIds`; each unsupported case has `supported: false`.

Example:

```json
{
  "question": "What was the Android stack for the delivery app?",
  "activeRole": "android",
  "history": [],
  "supported": true,
  "expectedSourceIds": ["resume-android", "case-study-dostava"]
}
```

- [ ] **Step 2: Write failing retrieval tests**

```ts
it('retrieves Dostava from a paraphrased technology question', () => {
  const result = retrieveEvidence({
    question: 'What was the Android stack for the delivery app?',
    history: [],
    activeRole: 'android',
    limit: 5,
  });
  expect(result.supported).toBe(true);
  expect(result.chunks.some((chunk) => chunk.projectId === 'dostava')).toBe(true);
});

it('carries sources into a short follow-up', () => {
  const result = retrieveEvidence({
    question: 'What else did he integrate?',
    history: [
      { role: 'user', content: 'Tell me about Northstar.' },
      { role: 'assistant', content: 'Northstar is a RAG service.', citationIds: ['github-northstar'] },
    ],
    activeRole: 'aiml',
    limit: 5,
  });
  expect(result.chunks.some((chunk) => chunk.projectId === 'northstar-rag')).toBe(true);
});
```

- [ ] **Step 3: Implement normalization and scored retrieval**

Build the retrieval query from the current question, up to two previous user messages, carried citation/project aliases, and a low-weight active-role token. Search with prefix/fuzzy matching only for terms longer than four characters. Boost exact alias/project matches heavily, titles moderately, and the active role slightly.

Mark `supported` only when one of these holds:

- an exact project/skill/screening alias matched a chunk; or
- the top score exceeds the calibrated evaluation threshold and at least two meaningful query terms overlap; or
- a follow-up carries a previously cited project/source and retrieves a chunk from that same evidence group.


Expected: 100% correct refusal classification for the eight unsupported cases and at least 90% source recall across supported cases. Record the threshold in a named constant with a test explaining the chosen boundary.

- [ ] **Step 2: Implement request/response schemas**

```ts
export const chatRequestSchema = z.object({
  question: z.string().trim().min(2).max(600),
  activeRole: roleIdSchema,
  history: z.array(z.object({
    role: z.enum(['user', 'assistant']),
    content: z.string().max(1_200),
    citationIds: z.array(z.string()).max(8).optional(),
  })).max(6),
  turnstileToken: z.string().min(1).max(2_048),
  sessionId: z.string().uuid(),
});
```

The model-answer schema limits answer length to 1,800 characters and follow-ups to three strings of at most 120 characters.

Define the public response exactly as:

```ts
export type ChatResponse = {
  requestId: string;
  answer: string;
  answerStatus: 'answered' | 'refused' | 'fallback';
  citations: Array<{ sourceId: string; label: string; href: string }>;
  followUps: string[];
  telemetry: {
    questionCategory: 'project' | 'experience' | 'research' | 'teaching' | 'screening' | 'skills' | 'unknown';
    latencyBucket: 'lt-500ms' | '500ms-2s' | '2s-5s' | 'gt-5s';
    modelId?: string;
  };
};
```

The telemetry object contains only normalized values already permitted by the analytics schema; it must not contain raw prompts, answers, retrieval scores, or internal errors.

- [ ] **Step 1: Write failing service tests for all outcomes**

- [ ] **Step 2: Implement the provider abstraction**

```ts
export interface AiProvider {
  generate(input: {
    messages: Array<{ role: 'system' | 'user' | 'assistant'; content: string }>;
    maxTokens: number;
    temperature: number;
  }): Promise<unknown>;
}

export function createWorkersAiProvider(ai: Ai, model: string): AiProvider;
```

Call `env.AI.run(model, ...)` with temperature `0.1`, a bounded token output, and JSON response format. Do not stream because the full structured response and citations must be validated before display.

- [ ] **Step 3: Implement the extractive fallback**

The fallback returns up to three top evidence statements, public citations, and a plain label explaining that generated synthesis is temporarily unavailable. It must never concatenate more than 1,800 characters or expose internal scores.

- [ ] **Step 4: Implement the orchestration service**

Order: retrieve → deterministic refusal if unsupported → build prompt → provider call → schema/citation validation → answer. Catch provider capacity/quota/timeouts and schema failures, map them to safe internal reasons, and return the evidence fallback. Never include raw provider errors in the response.
